# Opciones de arquitectura gestionada para el MVP

Consulta: **2026-09-09**. Precios en USD, sin impuestos, y sujetos a cambio. Este informe compara opciones; no toma la decisión del ticket.

## Condicionantes del MVP

- Beta cerrada bilingüe, dos devs, acceso por invitación/magic link, aislamiento estricto por Beta tester y borrado de cuenta.
- Una Knowledge revision es inmutable; extracción, chunking e indexación ocurren en `draft`, y una Knowledge publication activa todos sus artefactos conjuntamente. Un fallo debe conservar la última publicación válida.
- El Assistant solo lee datos y devuelve respuestas/propuestas estructuradas; no confirma cambios. Las citas y la procedencia son datos de dominio, no una función propietaria del proveedor de LLM.
- Los PDF deben subirse directamente a object storage. Vercel limita cuerpos de Functions a 4,5 MB; Supabase recomienda TUS por encima de 6 MB. [Vercel limits](https://vercel.com/docs/functions/limitations), [Vercel client uploads](https://vercel.com/docs/vercel-blob/client-upload), [Supabase uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads).
- Antes de crear embeddings masivos de material de Riot debe confirmarse que la autorización/licencia cubre RAG; el informe previo de fuentes no acredita por sí solo ese derecho.

## Procesamiento asíncrono

Flujo portable para PDF e importaciones: `upload directo -> fila job + mensaje con IDs -> descarga en worker -> antivirus/tipo/tamaño -> extracción determinista -> chunks/metadatos -> embeddings por lotes -> validación -> draft listo`. Cada etapa escribe estado, intento, error y checksum; usa una clave idempotente `(revision_id, stage, input_hash, pipeline_version)`. La publicación final debe ser una transacción corta que comprueba que todos los artefactos pertenecen a la revisión y cambia el puntero activo; nunca se publica desde el callback del LLM.

## Búsqueda híbrida

La solución más reemplazable es Postgres 18 full-text + `pgvector`, no un vector DB aparte. Supabase documenta `tsvector` + GIN para palabras, `vector` + HNSW para semántica y fusión por **Reciprocal Rank Fusion (RRF)**; pgvector recomienda la misma combinación y admite búsqueda exacta o HNSW/IVFFlat. [Supabase hybrid search](https://supabase.com/docs/guides/ai/hybrid-search), [PostgreSQL FTS](https://www.postgresql.org/docs/current/textsearch.html), [pgvector](https://github.com/pgvector/pgvector).

- Filtrar siempre por Knowledge publication activa, autoridad, idioma, vigencia y tipo de Knowledge source. Los drafts y revisiones retiradas no entran en candidatos.
- Mantener `fts_es` y `fts_en` (o configuración por fila) y consultar ambos cuando la pregunta y la fuente difieran de idioma; RRF evita comparar directamente escalas incompatibles de `ts_rank` y distancia vectorial.
- Empezar con vector exacto si el corpus es pequeño. HNSW mejora latencia pero consume más memoria y sacrifica recall; además, los filtros se aplican después del ANN y pueden devolver menos filas. Medir recall contra búsqueda exacta antes de indexarlo.
- Versionar cada embedding con `provider`, `model`, dimensiones, pipeline/chunk version y hash de texto. Cambiar de modelo requiere re-embed/index paralelo, no conversión matemática fiable. `vector` indexa hasta 2.000 dimensiones y `halfvec` hasta 4.000 con HNSW.
- Guardar fragmento, posición/página y procedencia en Postgres; construir las citas desde IDs recuperados y validar que cada cita pertenece a la publicación activa. El LLM no inventa URLs ni decide autoridad.

## LLM y embeddings

Usar una interfaz propia (`generateGroundedAnswer`, `embedDocuments`) o Vercel AI SDK con schemas Zod. AI SDK ofrece una API común y proveedores oficiales para OpenAI, Google y Mistral, pero la abstracción no elimina diferencias de tool calling, JSON Schema, tokenización, rate limits ni calidad. [AI SDK providers](https://ai-sdk.dev/docs/foundations/providers-and-models), [tools + structured output](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data).

Los rate limits son por cuenta/tier y no quedan garantizados por tener saldo; deben descubrirse en la cuenta contratada y protegerse con concurrencia, timeout, retry con jitter y fallback explícito.

## Trade-offs que debe resolver el ticket

| Eje | Un extremo | El otro extremo |
|---|---|---|
| Carga operativa | Vercel + Supabase concentra Auth/RLS/Storage/Postgres y acelera la beta. | Neon/R2/Auth separado o Railway reduce dependencia, pero añade integración y guardias de seguridad. |
| Suelo de coste | Cloudflare + Neon scale-to-zero puede acercarse a $5/mes; Railway parte de $5 pero cobra recursos activos. | Vercel + Supabase Pro parte aproximadamente de $45-$65/mes para una operación comercial persistente. |
| PDF/jobs | Trigger.dev ofrece runtime largo, binarios y un salto Hobby de $10. | Supabase/Cloudflare primitives abaratan y acercan estado, pero añaden límites de CPU/runtime; Inngest tiene mejor free tier que su salto Pro de $99. |
| Portabilidad | SQL/FTS/pgvector, S3, schemas Zod y estado de Conversation propio facilitan migrar. | Auth gestionado, primitives de cola/workflow y APIs stateful del proveedor aceleran hoy pero elevan el coste de salida. |
| Búsqueda | Exacta + RRF es simple y medible para corpus pequeño. | HNSW baja latencia al crecer, a cambio de RAM, tuning y recall aproximado bajo filtros. |
| IA | OpenAI ofrece embeddings muy baratos y schemas estrictos maduros. | Mistral ofrece inferencia barata, OCR y mejor vía open-weight; Gemini añade otro fallback pero su free tier tiene condiciones de datos distintas. La evaluación del dominio debe desempatar. |

## Decisiones aún abiertas, sin resolver aquí

1. Presupuesto mensual objetivo y si ambos devs necesitan asiento de deploy en Vercel.
2. Tamaño/número máximo de PDF, volumen de Knowledge revisions e importaciones y tiempo aceptable hasta `draft ready`.
3. Región y requisitos de tratamiento/retención de datos para DB, objetos, jobs y prompts.
4. RPO/RTO, backups, retención de logs y disponibilidad mínima; los free tiers no ofrecen una base equivalente a producción.
5. Resultado de la evaluación bilingüe y permiso escrito para almacenar fragmentos/embeddings de las fuentes oficiales.
